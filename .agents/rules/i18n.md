# i18n (rust-i18n)

- **`locales/en.toml` is the English source of truth.** Call sites use stable
  product-domain semantic keys such as `device.connected`, while each locale
  stores its text under the matching domain table. When adding a message, add
  the **same key to every** `locales/<code>.toml` in the same change, at the
  **same position** —
  the parity test enforces both order and key set so catalogs stay diff-aligned.
  Changing English copy does not rename the key.
- Values for non-English locales may be a best-effort translation (or temporarily
  match English when no better string is ready). Upstream OpenLogi's translators
  improve them there; do not leave keys missing — the parity test fails the build.
- TOML is parsed at **compile time** — a syntax error fails the entire GUI
  build. Catalog values are TOML basic strings grouped under stable
  product-domain tables.
- The locale key test (`openlogi-ui/tests/catalog_parity.rs`,
  `locale_files_have_the_same_keys`) requires every non-English file to carry
  **exactly** the keys in `en.toml` (no lag, no extras), in the same order and
  with the same interpolation placeholders.
- Adding a locale: drop the `.toml` in `crates/openlogi-ui/locales/` and add the
  `SUPPORTED` entry in `openlogi-core`'s `locale.rs` (picker order: native-name
  alphabetical per script). The parity test's `include_str!` list must grow too —
  it asserts its own coverage against `SUPPORTED`, so forgetting fails the build
  rather than silently leaving a catalog unchecked.
- Check with `cargo test -p openlogi-ui locale` (catalog parity, runs everywhere)
  and `cargo test -p openlogi-desktop i18n` (end-to-end key resolution; CI's Linux
  tests exclude the app crate, so that one runs locally). The overlay and agent each resolve one semantic
  key in their `the_shared_catalog_is_wired_up` test, so a broken relative
  `i18n!` path fails loudly instead of silently serving English.
